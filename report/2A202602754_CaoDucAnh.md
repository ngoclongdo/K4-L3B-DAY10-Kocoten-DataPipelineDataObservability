## 4. Giải thích phần kỹ thuật đã thực hiện

### Vấn đề cần giải quyết

1. Crossref API có thể trả về lỗi `429 Too Many Requests` hoặc gặp sự cố ngắt kết nối mạng làm gãy toàn bộ pipeline.
2. Dữ liệu thô từ API chứa nhiều mã định dạng HTML/XML rác (`<jats:p>`, `<jats:title>`), khoảng trắng thừa, định dạng ngày không đồng nhất (`date-parts` đa tầng).
3. Đảm bảo nguyên lý bảo tồn dữ liệu thô (Raw Preservation) để làm điểm neo Data Lineage cho quá trình phục hồi (Repair) sau này.

### Cách triển khai

1. **Ingestion & Fallback:**
   - Trong `fetch_source_records()`: Kiểm tra cờ `settings.refresh_source`. Nếu `True`, gọi HTTP request tới Crossref API; nếu gặp lỗi mạng hoặc HTTP 429, tự động bắt exception và fallback sang đọc file snapshot cục bộ tại `settings.paths.raw_api_response`.
   - Bóc tách payload JSON trong `parse_crossref_payload()`: Xử lý mảng `author` (ghép họ tên), chuẩn hóa ngày tháng `date-parts` thành `YYYY-MM-DD`, loại bỏ các thẻ HTML rác bằng regex `re.sub(r"<[^>]+>", " ", raw_abstract)`.
   - Lưu 2 file raw artifacts: toàn bộ payload gốc và danh sách `PaperRecord`.

2. **Cleaning & Pre-embed Modeling:**
   - Trong `build_clean_dataframe()`: Tính `age_days = (run_date.date() - pub_date).days`.
   - Ghép nối trường `text_for_embedding` gồm 5 trường: `Title`, `Authors`, `Published`, `Categories`, `Summary`.
   - Thực hiện `df.drop_duplicates(subset=["paper_id"], keep="first")` và sắp xếp theo `paper_id` để đảm bảo tính tất định (deterministic).
   - Xây dựng hàm `repair_from_raw_snapshot()` để đọc lại từ snapshot thô và tái tạo DataFrame sạch mà không cần gọi lại external API.

## 5. Một quyết định kỹ thuật quan trọng

- **Bối cảnh:** Cần quyết định cách thức xử lý khi hệ thống gọi API Crossref nhưng gặp lỗi mạng hoặc vượt ngưỡng giới hạn tần suất truy cập (Rate Limit 429).
- **Các phương án đã cân nhắc:**
  1. *Phương án 1:* Dừng pipeline ngay lập tức (raise exception) và yêu cầu người dùng cấu hình lại API key / đợi hết rate limit.
  2. *Phương án 2:* Thực hiện fallback tự động đọc snapshot dữ liệu có sẵn tại `data/raw/crossref_response.json` đồng thời ghi log cảnh báo.
- **Phương án đã chọn:** Phương án 2 (Cơ chế Cứu hộ Offline / Fallback).
- **Lý do:** Đảm bảo tính sẵn sàng cao (High Availability) và khả năng tái lập (Reproducibility) của pipeline. Trong môi trường production hoặc thực hành bài lab, việc không phụ thuộc 100% vào mạng ngoài giúp các bước kiểm định downstream (Observability, Indexing, Evaluation) diễn ra liên tục, không bị nghẽn.
- **Bằng chứng quyết định phù hợp:** Pipeline chạy mượt mà ngay cả khi ngắt mạng, trích xuất chính xác 24 bài báo mẫu phục vụ cho toàn tuyến.

## 6. Một lỗi hoặc blocker đã xử lý

- **Triệu chứng/lỗi nguyên văn:**
  ```text
  UnicodeEncodeError: 'charmap' codec can't encode character '\u1ec7' in position 6: character maps to <undefined>
  ```
- **Lệnh hoặc bước tái hiện:** Chạy lệnh kiểm tra bằng Python inline script in chuỗi có chứa dấu tiếng Việt `"Tín hiệu hoàn thành..."` trên terminal PowerShell/cmd của Windows.
- **Nguyên nhân gốc:** Bảng mã mặc định của Windows console sử dụng codepage `cp1252`, không hỗ trợ đầy đủ các ký tự Unicode tiếng Việt có dấu khi in qua stdout.
- **Cách xử lý:** Đặt biến môi trường `set PYTHONIOENCODING=utf-8` trước khi thực thi lệnh Python qua cmd/PowerShell:
  `cmd /c "set PYTHONIOENCODING=utf-8 && venv\Scripts\python ..."`
- **Cách xác minh sau khi sửa:** Lệnh thực thi thành công exit code 0 và console in đầy đủ chuỗi tiếng Việt rõ ràng.
- **Điều học được:** Khi phát triển pipeline trên môi trường Windows đa nền tảng, luôn cần quản lý encoding (`utf-8`) ở cả tầng I/O file và tầng stdout/stderr của tiến trình terminal.

## 7. Hiểu biết về luồng end-to-end

Giải thích ngắn gọn bằng lời của bạn:

1. **Dữ liệu đi từ Crossref đến vector index như thế nào?**  
   Dữ liệu được thu thập từ Crossref REST API (hoặc fallback snapshot) -> Lưu trữ nguyên bản tại `crossref_response.json` (Lineage Anchor) -> Bóc tách thành `PaperRecord` -> Chuẩn hóa, khử trùng lặp và làm giàu văn bản thành `text_for_embedding` trong DataFrame -> Chuyển thành vector embeddings bằng mô hình `all-MiniLM-L6-v2` và nạp vào ChromaDB collection.
2. **Evaluation set và ground-truth document IDs dùng để đo retrieval/answer quality ra sao?**  
   Evaluation set bao gồm 10 câu hỏi chia đều qua 4 nghiệp vụ (`summary`, `authors`, `date`, `categories`). Mỗi câu hỏi có `ground_truth` và `ground_truth_doc_ids` (DOI chuẩn). RAG Agent truy vấn vector index để lấy top-k context; `retrieval_hit_rate` đo xem tài liệu chuẩn có nằm trong top-k hay không, và `mean_token_f1` đo độ trùng khớp giữa câu trả lời sinh ra và ground truth.
3. **Quality checks khác freshness monitoring ở điểm nào trong bài lab?**  
   Quality checks (Great Expectations 1.x) kiểm tra tính toàn vẹn về cấu trúc và schema của dữ liệu (số dòng, not null, unique, độ dài tối thiểu). Freshness monitoring giám sát khía cạnh thời gian (temporal quality), cảnh báo dữ liệu bị lỗi thời (stale) dựa trên SLA ngưỡng tuổi đời bài báo (`age_days > 180`).
4. **Vì sao phải dùng cùng test set cho baseline, corrupted và repaired?**  
   Để đảm bảo tính khách quan và hợp lệ của phép thử (controlled experiment). Cùng một bộ đề kiểm tra giúp đo lường chính xác tác động tiêu cực của Data Corruption và mức độ hồi phục thực sự sau khi Repair.
5. **Repair được xem là thành công dựa trên artifact và metric nào?**  
   Repair thành công khi: (1) Data Quality Gate pass lại (`success = True`); (2) Freshness SLA phục hồi (`is_fresh = True`); (3) Các chỉ số `retrieval_hit_rate` và `mean_token_f1` trong `repaired_metrics.json` khôi phục tiệm cận hoặc bằng mức ban đầu trong `baseline_metrics.json`.

### Kết luận từ số liệu

Hoàn thành hai chuỗi nguyên nhân–bằng chứng sau:

1. Data corruption → quality/freshness signal thay đổi: Vi phạm GX và SLA cảnh báo stale → agent metric thay đổi: Hit rate và Token F1 sụt giảm nghiêm trọng.
2. Repair action: Tái tạo DataFrame từ raw snapshot → quality/freshness signal phục hồi: GX 1.x pass trở lại → agent metric phục hồi: Vector store được re-index và Agent đạt lại độ chính xác cao.

## 9. Điều học được và hướng cải thiện

### Ba điều quan trọng nhất

1. **Về Data Pipeline:** Hiểu rõ tầm quan trọng của nguyên tắc Bảo tồn dữ liệu thô (Raw Preservation) và tính Idempotent; giữ snapshot gốc nguyên bản là điều kiện tiên quyết để có thể tự động phục hồi hệ thống khi có sự cố.
2. **Về Data Quality/Observability:** Nắm vững cách thiết lập Data Quality Gate theo chuẩn mới của Great Expectations 1.x với Ephemeral Context và cách xây dựng SLA giám sát độ tươi mới của dữ liệu.
3. **Về ảnh hưởng của Data đến RAG:** Thấy rõ hiện tượng "Garbage In, Garbage Out" và Silent Failure trong RAG; khi dữ liệu đầu vào bị rác hoặc mất trường, LLM sẽ trả lời sai hoặc ảo giác dù hệ thống không hề ném ra runtime error.

### Nếu có thêm thời gian

Xây dựng cơ chế Circuit Breaker tự động: Khi phát hiện Quality Gate vi phạm hoặc Freshness SLA bị breach, pipeline sẽ tự động rollback vector collection về phiên bản snapshot gần nhất và gửi webhook thông báo qua Slack/Discord.
